# Reflection (approximately 400 words)

The Placement Eligibility Checker addresses a repetitive task in a college placement cell. Companies describe eligibility in different ways, so staff may need to read every post, identify branches and academic cut-offs, and compare those requirements with student records. Doing this manually takes time and can lead to mistakes. My project creates a draft list for each job while keeping the final decision with a human placement officer.

The main design decision is to separate language understanding from student matching. The language model receives only the job-post text and returns five fields in JSON: branches, minimum CGPA, maximum backlogs, batch, and a short summary. Student records are loaded and processed by Python locally. This boundary is important because the student list contains personal information and is not needed to interpret a job post. The code does not send student names, roll numbers, CGPAs, or backlog records to the model.

I also learned that a model response cannot be trusted automatically just because it looks like JSON. The program checks that the response has exactly the required fields, valid types, allowed branch names, and a short summary. It then checks extracted facts against the original post. If the API call or validation fails, the program retries once and then uses a conservative local fallback. If the post does not provide a verified branch or CGPA cut-off, the job is marked `needs_review` rather than pretending that the requirements are known. A percentage is not converted into a CGPA, and vague wording such as “top 10 percent” is not treated as a numerical CGPA rule.

Testing is essential because an incorrect result can harm students in different ways. A wrongly excluded student could miss an opportunity, while a wrongly included student could appear on an inaccurate list sent to a company. The project therefore produces draft CSV and text reports rather than contacting companies or making final decisions. The placement officer must compare every list with the original job post before it is shared.

The current version is a coursework prototype, not a production placement system. Its fallback parser uses simple text patterns and may not understand every way a company phrases its requirements. The sample student records are fictional, and real deployment would need faculty approval, stronger tests, access controls, and an agreed privacy policy. API cost and response time also depend on the selected model and provider. These limitations should be discussed honestly during the demonstration.

Overall, this project taught me to treat AI as one component in a larger system. A useful AI application needs validation, fallback behaviour, privacy boundaries, repeatable tests, and human accountability—not only a prompt that produces a plausible answer.
